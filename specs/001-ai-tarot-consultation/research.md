# 조사: AI 타로 상담 서비스 MVP

## 결정: MVP 카드 해석은 결정적 문서 조회를 사용한다

**근거**: MVP는 메이저 아르카나 22장, 정방향, 3개 위치만 사용한다. 문서 규모가 작고 통제 가능하므로 card, orientation, position, active flag, document version 기준 직접 조회가 벡터 검색보다 재현성이 높다.

**검토한 대안**: FAISS, pgvector, Qdrant. 이들은 더 큰 컨텍스트 보강에는 유용하지만 핵심 카드 의미 조회에는 운영 복잡도가 과하다.

## 결정: 컨텍스트 검색은 선택 기능으로 둔다

**근거**: 고민 카테고리별 일반 컨텍스트는 어조와 관련성을 높일 수 있지만, 카드 의미 문서만으로도 MVP의 핵심 해석은 가능하다.

**검토한 대안**: 필수 RAG, 검색 완전 제외. 선택 검색은 MVP를 단순하게 유지하면서 품질 개선 경로를 남긴다.

## 결정: 상담 생성과 SSE 구독을 분리한다

**근거**: 브라우저는 GET 기반 SSE를 자연스럽게 처리한다. 상담을 먼저 생성하면 안정적인 consultationId를 확보하고, 멱등 재시도와 저장 처리를 명확히 하며, live stream이 끊겨도 서버가 가능한 경우 생성을 완료할 수 있다.

**검토한 대안**: POST 요청 자체를 스트림으로 사용. 이 방식은 재시도, 인증, 저장 처리를 복잡하게 만든다.

## 결정: 프론트엔드, 백엔드, AI 서버를 분리한다

**근거**: 백엔드는 인증, 권한, 저장, SSE 중계를 담당한다. AI 서버는 prompt 구성, LLM 호출, JSON 검증, 모델 관찰성을 담당한다. 이 분리는 팀 책임과 기술 생태계에 맞다.

**검토한 대안**: 백엔드 단일 서비스에서 직접 LLM 연동. 초기에는 더 단순하지만 Python 기반 AI 도구와 평가 체계를 적용하기 어렵다.

## 결정: refresh, draft, rate limit, idempotency 보조 데이터는 Redis를 사용한다

**근거**: 이 데이터는 TTL이 필요하고 변경 빈도가 높은 단기 상태다. Redis는 refresh whitelist, draft deck 만료, 로그인 제한, 중복 요청 처리에 적합하다.

**검토한 대안**: MySQL만 사용하는 방식. idempotency에는 가능하지만 draft TTL과 rate limit counter에는 덜 적합하다.
